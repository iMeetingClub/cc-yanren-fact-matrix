自由讨论 4：商城需求与任务管理
事实
1. 商城需求已完成，但用户付款信息在平台上不可见。
2. 两条记录已经在 Kimi 的转账记录上了，涉及积分任务。
判断
1. 需要一个接口来核实用户的付款情况，否则需要人工核算。
2. 当前任务每天生成，批量生成功能需要增强以便周期性任务管理。
3. 当初在做钱包的时候并没有写付款接口功能。
4. 共创营内容需要手动检查付款情况。
5. 如果任务系统本身还没完成，进行测试或运营会影响用户体验。
6. 即使资金充足，也很难在短时间内完成任务。
7. 一对一拼音交易可能需要转向平台交易以简化流程。
8. 实现时效记录显示功能需要技术确认。
观点
1. 操作简单能提高使用频率，形成使用习惯。
2. 操作复杂会降低使用频率，影响平台的易用性。
3. 付款接口应该早就提供，晚改麻烦且费用高。
4. 社区任务系统完善能体现 NT 的价值。
5. 通过CI处理交易转账是简单直接的方法。
建议
1. 补充商城平台的付款核实功能。
2. 增强任务管理的批量生成功能以提高效率。
3. 调整平台的三维接口以确认付款。
4. 通过API在平台上显示付款信息以减少手动检查。
5. 建议与刘斌商量，将其作为专项资金来完善任务系统。
6. 考虑从一对一拼音交易转向平台交易机制，进行周期性结算。
7. 通过技术手段实现时效记录显示。

3. 商城的逻辑是否与任务的逻辑相同，即转账后需要手动确认？
4. “购买锁单”是什么意思？
5. “确认收款并下架”是什么意思？
6. “取消锁单，重新上架”是什么意思？
7. 当前页面是否显示哪些人已经购买了这些记录？
8. 当我取消下架时，之前的支付是否依然存在，除非我手动取消？
9. 取消下架后，砚仁付给我的积分是否需要我私下再转给他，才算退款？
答问要点
1. 商城可以跳转到支付界面，但支付速度较慢。
2. 支付完成需要确认，可能由于密码错误导致延迟。
3. 屏幕共享时有误，需要重新共享整个屏幕。
4. 商城的支付涉及活动部分，付款后需手动确认是否承担费用。
5. 商城支持一物一拍功能，自动跳转钱包进行付款。
6. 付款后如果对方确认收款，商品会自动下架。
7. 如果对方未收款，或线下协商不购买，卖家退钱并重新上架。
8. 功能依赖线下交互，智能合约可选。

自由讨论 6：批量任务与系统可行性讨论
事实
1. 任务部分展已经做好了自动上链付款功能，可以直接调用。
2. 云展那边已经有一版实现了每一场活动的开始时刻、结束时刻、报名开始时刻可查看的功能。
3. 这个平台是开发者社区的一个项目。
4. 周期性任务可以在日历上显示。
5. 丹尼会写Python，对区块链有一定了解。
判断
1. 批量任务相对单一任务更容易处理，因为逻辑函数线已经有了。
2. 从技术角度来看，系统是可行的，可能在一周内完成开发。
3. 直播的批量任务技术与活动的批量生成相似。
4. 任务包与批量任务存在相似但有区别的地方。
5. 云展的任务池与设计的矩阵结构不同，任务池是树状结构。
6. 每天的任务并不是重复的，任务按天数统一创建。
7. 课程任务类型差不多，只是时间有一些变化。
8. 江可能已经完成了一些API的开发。
观点
1. 如果系统功能完善且有助于任务平台，可以考虑使用。
2. 将其视为任务和活动的复合版，有些奇怪。
3. 活动功能已经比较完善，用户可以自行探索。
4. 批量安排任务有点麻烦，但不是不能用。
5. 只要觉得有必要且合理就可以做。
建议
1. 批量任务和单一任务应该分开管理，另一个按钮只有管理员可以发布。
2. 如果批量任务被取消并要求退款，需要自行处理退钱。
3. 可以先着手确定 UI 或者 UX 方面的位置按钮以复用相关逻辑。
4. 希望云展能够实现一键发布任务的功能。
5. 在任务后面的审核部分需要再检查逻辑。
6. 需要解决没有转账记录的问题，建议先在线下和线下合并处理。
7. 可以考虑提供一个API作为CI之前的附加部分。
8. 可以去问一下丹尼的意见。

自由讨论 7：任务提醒与管理系统
事实
1. 任务提醒系统可以通过消息中心提示已接任务和待完成任务。
2. 日历功能可以帮助用户查看任务的截止时间。
3. 周期性任务可以按不同颜色标识。
4. 重复任务可以在特定时间内多次进行。
5. 提醒功能仅限于网页内，用户必须打开网页才能看到提醒。
6. 消息中心有文字记录功能。
7. 会议提醒可以在结束前1小时进行调整。
判断
1. 实时提醒功能对普通任务管理很重要。
2. 没有日历功能，查找任务截止时间会很麻烦。
3. 重复任务在很多真实场景下是有必要的。
4. 如果所有任务都上日历，日历会显得过于拥挤。
5. 只上自己领的任务可能失去提醒功能。
6. 现有系统逻辑上存在问题。
观点
1. 日历功能对短期任务管理很方便。
2. 日历没有必要，可以在页面合理摆放任务信息。
3. 希望系统能变得更有趣。
4. 项目好玩与否不在于平台设计，而在于简洁、有效、顺手。
建议
1. 后台应实时提醒用户去完成任务。
2. 应在消息中心提示用户已接任务和待完成任务。
3. 建议日历功能可以标识周期性任务的时间段。
4. 在前端 UI 部分标识出任务的领取时间。
5. 考虑如何更好地处理重复任务，尤其是复杂任务。
6. 可以调整会议提醒时间为结束前3小时或5小时。
7. 仅将自己接的任务上日历以减少拥挤。
8. 周期性任务应清晰展示并与一次性任务区分。

自由讨论 10：开发者社区资金激励
事实
1. 与刘斌开始沟通开发者社区事宜。
2. 未付的款项是用于开发者社区的投资。
3. 剑桥表示开发者社区有需求时可以申请资金。
4. 开营时间一开始是从5月中旬。
5. 目前报名的人数意向已经有十六个，比第一期和第三期增加了一倍。
6. 第二期收费三百，当前一期收费六百。
7. 之前收费1500元时无人报名。
判断
1. 刘斌对开发者社区资金激励方案持积极态度。
2. 盈利要达到80%并且亏损20%以内，才能算比较成功，也才有投资的可能。
3. 工长银之前因为资金没到位，一直拖延。
4. 几乎很难达到盈利目标。
5. 合作的成本是主要支出，包括电费、推流等。
观点
1. 需要新的资金作为任务系统的激励。
2. 只要钱到位了，就都好说。
3. 如果尝试了，但最终没成功，那也没有意义。
建议
1. 先观察任务系统的实际效果，再决定是否投入资金。
2. 流程是社区申请资金，然后资金到账后用于激励。
3. 提案需通过才能进行后续工作。
4. 完成任务后需进行回溯性激励。
5. 确认激励能够到账后再向开发者社区申请。
